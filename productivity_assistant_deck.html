The experiment

The rollout

Pilot with one admin first

The pilot starts with an admin who already lives in this dashboard and asks these questions every week. They will tell us straight whether asking beats clicking around.

We sit with them first and collect the questions they actually ask. Those become the suggested prompts and the test set. We are not inventing questions in a conference room.

What going well looks like

  • They open it on their own, more than once a week, unprompted
  • Answers match the dashboard exactly, tested continuously, not by vibes
  • At least one real decision happens because the assistant surfaced something
  • Their question list keeps growing, which means they trust it enough to push it

Production lessons · Shopify Sidekick

The playbook already exists

  • One simple agent with good tools beat predefined workflows and multi-agent designs for an in-admin assistant on Rails
  • Just in time instructions: tool guidance rides in tool responses, not in a bloated system prompt. Lean, cache friendly, no death by a thousand instructions
  • Preview and commit: the AI proposes, the human signs off. Sidekick never mutates shop state directly
  • Evals, not vibes: real labeled conversations, measured agreement, iterated. Vibe testing is how quality quietly rots

Tool design

Few tools, rich parameters

  • An earlier sketch had 19 tools. Overlapping tools are how models pick the wrong one. Consolidation collapsed them to 5, parameters do the work
  • Tools accept human names, never internal IDs. Models mangle opaque identifiers, and an admin says Gary, not auditor 42
  • Parameters constrain rather than guess: valid names live in the tool schema, ambiguity comes back as a clarifying question
  • Every tool reuses the same authorization and the same query objects the dashboard renders from. Chat answers and on-screen numbers cannot disagree

Trust

Guardrails before cleverness

  • Deterministic code computes every number. The model selects tools and narrates. Number fidelity is asserted in evals
  • Write actions wait for the next rung, and arrive behind preview and commit when they do
  • Chat history lives in Postgres under the same retention rules as the rest of the audit database
  • A defined lane: productivity, workload, and quality score questions. Everything else gets a polite decline
