Productivity Assistant

architecture brief · read-only Q&A over the productivity dashboard · 2026-08-03

A chat rail embedded in the productivity dashboard lets admins ask questions in plain English. The model picks which question is being asked and narrates the answer. It never computes the numbers. Every figure comes from the same query objects the dashboard already renders from, and every model call stays inside the AWS compliance boundary via Bedrock. The model itself is a config choice, not an architectural one.

System anatomy

Chat rail frontend

Stimulus + Turbo. A collapsed rail on the left of both dashboard tabs that expands into a column and pushes the content over, so nothing gets covered while you chat. Survives tab navigation (turbo-permanent) and renders only for allowlisted admins until GA.

Assistant controller entry point

Same Pundit policy as the dashboard. Persists the user message and enqueues the job. Thin by design, no AI logic lives here.

Agent loop core

A Sidekiq job runs the RubyLLM loop: replay history from Postgres, call Bedrock, execute whatever tools the model requests, repeat until the answer is complete. Chats, messages, and tool calls all persist via acts_as_chat.

Tool layer the seam

Plain Ruby objects carrying the acting user for authorization. Each tool wraps an existing query object and returns structured data plus just-in-time instructions. This is the portable convention future surfaces reuse.

Query objects source of truth

Productivity::Completions and Productivity::Workload already power the two tabs. The assistant reads the exact same code path, so chat answers and on-screen numbers cannot disagree.

Streaming path delivery

Answer chunks broadcast over the existing Action Cable + Redis setup into the rail. The first chunk creates the DOM target. No new infrastructure.

Decided

RubyLLM 1.16.x on the Bedrock provider stack

Chat, tools, streaming, structured output, and Rails persistence in one gem. Model-agnostic by construction: RubyLLM abstracts providers and Converse abstracts models, so swapping models or labs is config, not code. Pinned for now with 2.0 revisited later.

Left rail, not right ux

The right edge is already owned by the drill-down drawer and the nav drawer. A left rail that pushes content means chat stays open through drill-downs and reassignments.

Trust guardrails scope

Read-only v1. Deterministic code computes every number and the model only narrates. Write actions wait for the next rung, behind preview-and-commit.

Evals from day one quality

Jill's real questions become a labeled set run against the live model on AI-touching PRs. Deterministic assertions: tool choice, arguments, number fidelity.

Credentials reuse the existing pattern ops

The app already reads AWS keys from env vars with encrypted-credentials fallback, and each environment has an IAM user in the staging AWS account. Non-prod attaches a scoped Bedrock policy to those users. Prod gets a dedicated user later. Review apps run with the assistant gated off.

Compliance boundary
Bedrock is what makes this possible with PHI in the building. Prompts and completions never reach any model vendor, nothing is trained on, and Converse content is not stored by default. HIPAA-eligible under our AWS BAA. The guarantees attach to Bedrock rather than the model, so model swaps keep the compliance story intact while leaving Bedrock would reopen it. Two design consequences: chat history in Postgres follows the same retention rules as the rest of the audit DB, and newer models need region-prefixed inference-profile IDs (us.) or Bedrock returns a 400. Verified live as of 2026-08-03: the staging account invokes Claude Sonnet 5 successfully, and the AWS Organizations BAA shows Active (effective 2026-06-02) in Artifact, covering all member accounts. Its two standing conditions, HIPAA-eligible services only and PHI encrypted in transit and at rest, are both met by this design.
