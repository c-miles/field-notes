Kopilot,
under the hood

How the productivity assistant is actually built. The choices, the plumbing, and why each piece is the way it is.

What we built

A chat rail that answers from the dashboard's own data

Admins ask questions in plain English, "who's overloaded right now?", and answers stream in beside the numbers they're asking about. Same read models the dashboard renders from, so the chat and the page can never disagree.

Read only

The assistant cannot change anything, and its prompt says so plainly.

Admin gated

System admins only for now, behind an environment kill switch. Production stays dark until we flip it.

Five tools

Productivity, workload, roster, scores, and time expectations, each wrapping an existing read model.

The one principle everything hangs on

Code computes.
The model narrates.

Every number in every answer was computed by deterministic Ruby before the model ever saw it. The model's job is phrasing, not arithmetic. That is why Kopilot cannot hallucinate a figure, the worst it can do is describe a real one badly.

01
Part one

The AI layer

RubyLLM, Bedrock, and why both.

RubyLLM

One gem, four jobs we didn't have to build

Provider abstraction

chat.ask looks the same on any model. Model choice is config, an env var, not code.

Rails persistence

The acts_as family makes chats, messages, and tool calls ordinary ActiveRecord models in our schema.

Tool calling

Subclass, declare params, implement execute. The gem runs the whole call loop with the model.

Streaming

Pass a block to complete and chunks arrive as they're generated.

Alternatives we weighed: langchainrb (heavier, weaker Rails story), the raw AWS SDK (no persistence, no tool loop, and AWS ships no Ruby examples), the official anthropic gem (no Rails layer). RubyLLM is the best documented Ruby path to Claude on Bedrock.

RubyLLM, eyes open

Limitations we've validated

We smoke tested every feature against Bedrock before building on it, and hit three real gaps, each with a workaround in place.

  • No history windowing. Every persisted message replays to the model on every ask. Our conversation rotation is the mitigation.
  • Prompt caching unreleased. The API exists upstream but hasn't shipped. Worth roughly 85 percent off input costs when it does.
  • Bedrock feature lag. Registry, thinking replay, and schema gaps found early, documented, and worked around.
Why Bedrock

PHI never leaves our AWS boundary

Bedrock is AWS's managed foundation model service. Claude runs inside an AWS owned account, Anthropic never sees our traffic, prompts are never used for training, and it's HIPAA eligible under the org's executed AWS BAA. Calling Anthropic's API directly was never on the table for this data.

BAAexecuted with AWS, the compliance foundation
IAMexisting AWS auth and billing, no new vendor
Zeroprompts shared with the model provider
Bedrock mechanics

What talking to it actually looks like

  • We speak the Converse API, Bedrock's unified chat endpoint, which is what RubyLLM's provider renders to.
  • Model IDs are cross region inference profiles. The us. prefix is required, base IDs fail with a 400.
  • No server side tools on Bedrock, so all tool execution is client side in Rails, which is what we want anyway.
# config/initializers/ruby_llm.rb
RubyLLM.configure do |config|
  config.bedrock_api_key = aws.access_key_id
  config.bedrock_secret_key = aws.secret_access_key
  config.bedrock_region = aws.region
  config.default_model =
    "us.anthropic.claude-sonnet-4-6"
end

The data model

Four tables, all ours, encrypted where it counts.

The schema

acts_as makes them ordinary ActiveRecord

The gem's macros wire the associations and teach each record to convert itself into the model conversation. We own the tables, the migrations, and the encryption, content and thinking text encrypt like evaluation notes do.

A consequence that shaped real code: encrypted columns can't be queried in SQL, so blank row filtering happens in Ruby after decryption.

The load bearing method

A chat row is not self sufficient

Tools live only on the in memory chat, and the system prompt embeds today's date, so it's a persisted row that gets rewritten when its text changes. prepared is the single seam that restores all of it. The answer job calls chat.prepared.complete, one method, nothing forgettable.

# app/models/kopilot/chat.rb
def prepared
  instructions = SystemPrompt.text
  with_instructions(instructions, ...)
  with_tools(
    *TOOLS.map { it.new(user:) }
      .select(&:allowed?)
  )
end
03
Part three

Tools

How the model reaches our data, and only our data.

The round trip

How a tool call actually happens

  1. The model reads each tool's description, its routing signal for when to reach for it, and its param schema.
  2. It decides to call one. The gem validates the arguments and invokes execute on our plain Ruby object.
  3. The tool checks its policy, runs its read model, and returns a hash payload, every number precomputed.
  4. The payload persists as a tool result message and goes back to the model, ending with a guidance string telling it how to read what it got.
  5. Rounds repeat inside one complete call until the model has what it needs, then it writes the answer.
The toolbox

Five tools, five read models

productivity

Completed output per auditor, priced into productive hours, period comparisons.

workload

Open work right now, plus the unassigned queue and how long it has waited.

roster

Who's qualified for what, per chart type and client, straight from specialties.

scores

Averages by client, chart type, coder, or auditor, with the 95 threshold verdict.

time_expectations

Expected minutes against observed medians, are our prices still right?

They compose. "Who should take this unassigned audit?" calls roster and workload together, eligible people first, then who has room.

A deliberate split

Description vs guidance

Two kinds of instruction, delivered at two moments. Descriptions are pick time: when to reach for this tool and when not to. Guidance rides every payload, read time: how to interpret these fields, zero versus unknown, when not to volunteer the unassigned queue.

Every payload also carries an as_of stamp, and the prompt tells the model to re-query rather than reuse a result from an earlier day. Data freshness is enforced, not hoped for.

Pick time

"Use it for questions about output, who completed how much, and period over period comparisons..."

Read time

"Every number here is precomputed, never add, average, or derive figures yourself..."

The system prompt

A few hundred words, deliberately small

  • Identity and lane. Productivity, workload, and scores. Politely decline everything else.
  • Shared vocabulary. Auditors vs coders, initial rounds vs monthly, what "meets threshold" means.
  • Panel rules. Answer at the scope of the question, tables only for what the dashboard doesn't show, no process narration.
  • The calendar. Today's date and week boundaries, the one thing a model can never know.

What's deliberately not in it

Tool specific knowledge lives in descriptions and guidance, not the prompt. Keeps the prompt stable and cacheable, and keeps each tool portable, ready for the MCP future where other clients drive the same tools.

04
Part four

The conversation

Persistence, lifecycle, and the streaming pipeline.

Lifecycle

Conversations persist, and rotate when stale

Everything persists encrypted, and on every ask the entire conversation replays to the model. That's the gem's reality, so lifecycle is our cost and freshness lever. We benchmarked the field, Amazon Q, GitHub Copilot, and Notion AI all persist and resume, none reset on a calendar.

  • Resume by default, with a new conversation button.
  • Rotate when stale: idle 12+ hours or 100+ messages, and only at send time, so page loads never strand orphan chats.
  • Rail renders the last 50 messages, the model keeps the rest until rotation.
End to end

From enter key to streamed answer

  1. Composer posts, the question persists immediately, and the answer job enqueues. The web request is done.
  2. Sidekiq runs the agent loop off the web thread, no retries, a per chat lock so two questions can't interleave.
  3. A thinking bubble with rotating phrases appears while tool rounds run, driven by the message lifecycle broadcasts.
  4. Chunks stream back, and every 50 characters the job re-renders the accumulated markdown into the bubble, tables assemble mid stream.
  5. Transport is Turbo Streams over ActionCable over Redis, WebSockets we already run. The finished answer replaces the bubble, fully formatted.
  6. Failures are honest: the stuck bubble clears and a plain "that answer didn't make it" appears. No eternal spinners.
Rendering choice

Progressive markdown, server side

The model writes GitHub flavored markdown. We render it with Commonmarker plus a tight sanitize allowlist, and re-render the accumulated text on each flush, the same full re-parse approach the big chat products use, done server side so sanitization lives in exactly one place.

Wide tables scroll in place inside the bubble. The rail never stretches, the page never scrolls sideways.

50 charsper re-render flush, not per token, saves Redis publishes and browser reflows
~1.3 msmeasured cost of one full markdown render, cheap enough to repeat
0 newJS dependencies, no client side parser, no second sanitize pipeline
The rail

The UI, briefly, and a caveat

Turbo permanent

Conversation, collapse, and width survive tab switches, the rail never re-renders on navigation.

Resizable

Drag the divider, 320 to 560px, with a viewport cap so the rail yields before the dashboard.

Keyboard

Cmd B / Ctrl B toggles it, the panel convention from the editors everyone uses.

Composer

Grows to six lines, shift enter for newlines, holds your question if a send fails.

The UI and UX are up for debate, feedback welcome. The architecture underneath is the settled part.
Guardrails

Dark by default, honest when it fails

  • KOPILOT_ENABLED env flag: absent means the assistant doesn't exist. Production and review apps stay dark.
  • KopilotPolicy owns who sees it, wherever it appears. System admins today, widens per surface later.
  • A Kopilot failure never takes the dashboard down, the page renders without the rail.

Expectation setting

Answer quality has known gaps. The eval harness is next, real transcripts are already catalogued as scenarios, and tool and prompt hardening rides those evals. Right now we're judging the plumbing, not the takes.
